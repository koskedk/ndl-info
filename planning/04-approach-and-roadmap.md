# Approach and roadmap

How the team builds NHAI: the working rules, the documents that are kept as data, the project layout, the engineering settings, and the order of work. It follows the technology discussion in `resources/Claude.pdf`, which is the reference where anything is unclear.

## Working rules

1. **One vertical slice first.** Take patient and encounter from all three EMRs through bronze, silver and gold before widening. The first slice proves every part; each later domain is faster because the macros, quality patterns and conventions already exist.
2. **Target-first.** Define each canonical table from what the indicators need, then map each source into it. Do not start from the richest source and force the others to fit.
3. **Documentation is data, not prose.** The four documents below live in tools and are generated or tested, so they cannot drift from the code.
4. **Lineage is generated, never drawn.** A hand-drawn lineage diagram is wrong within a month.
5. **Flag, do not guess.** Where source documents disagree or are silent, record the question and leave the value empty. Every mapping cites the document it came from.
6. **Only build what an indicator uses.** A column stays in bronze until an indicator needs it. Quality rules are written for columns indicators depend on, not for every column.

## The four documents kept as data

| Document | What it holds | Where it lives |
|---|---|---|
| Source-to-target mapping spec | One row per silver column: source system, source table and column, transformation rule, code set, quality rule, how personal data is treated | Starts as a spreadsheet; becomes the YAML beside each dbt staging model |
| Data contracts | For each silver table: what one row means, its keys, and which source wins when sources disagree | dbt model YAML, shown in the data catalog |
| Quality rules catalogue | Each rule's ID, severity, threshold and the indicators it protects | dbt tests and Soda Core checks |
| Lineage | Where every table and column comes from | Generated by dbt; column-level view in OpenMetadata |

## dbt project layout and naming

```
models/
  staging/<source>/     stg_<source>__<entity>      one per source and entity, canonical output shape
  vault/                hub_*, link_*, sat_*, pit_*  patient, facility, encounter
  intermediate/         int_<entity>_unioned        events from all sources stacked
                        int_<entity>_resolved       identity and conflict rules applied
  silver/               silver_<entity>             the Canonical Health Data Model
  gold/dimensions/      dim_*
  gold/facts/           fact_*
  gold/marts/<programme>/                           malaria, rmncah, later hiv, tb, supply_chain
seeds/                  ref_<thing>_map             code mappings: source system, source value, canonical code
macros/                 soft-delete filter, time-zone conversion, hashing, vault loaders
```

- **Shared macros are written once**, in the bronze phase: dropping soft-deleted rows (`voided`, `docstatus`), converting to UTC, hashing identifiers.
- **Sources are named in SQL as they are in the `explorer` tool**: `kenyaemr`, `amrs`, `tiberbu`, `khis`.

## Engineering settings

| Setting | Value | Why |
|---|---|---|
| Bronze tables | Split by source system and pick-up date; `bronze_load_id` and the source snapshot ID on every row | Replay, and tracing any row back to its load |
| Fact tables | Split by source system and month of the event; sorted by `person_key` within files | Fast patient-level joins and monthly queries |
| Satellites | Split by source system and load date | Matches how they are loaded |
| File format | Parquet with zstd compression; target file size 256 to 512 MB | Object stores perform badly with millions of tiny files |
| Raw-vault tables | Loaded by append | Insert-only by design |
| Conformed and business tables | Loaded by merge | Rows are updated as rules or sources change |
| Schema changes | New source columns are added automatically (`on_schema_change: append_new_columns`) | Sources add fields without warning |
| Table upkeep | After each load: merge small files. On a schedule: expire old snapshots (keep 30 to 90 days in silver, longer in bronze) and remove stray files | Keeps reads fast and storage bounded |
| Restricted area | Raw identifiers in their own namespace, `silver_restricted`, with access controlled in the catalog | Keeps personal data apart from analysis |
| After every load | dbt tests and Soda checks run; dbt docs are published; OpenMetadata is refreshed | Quality and documentation stay current |
| Trino | Native S3 access with path-style addressing; workers given local SSD for spill | Vault joins and patient matching spill to disk |
| Patient matching | Splink on DuckDB for the proof of concept, Spark at scale; results written back as the same-as link | Trino is not the tool for scored matching |
| Development | dbt can run on DuckDB against the same Iceberg tables while volumes are small | The models do not change when moving to Trino |

## Roadmap

The phases follow the technology discussion. The weeks assume a small team working on it continuously and are for sequencing, not commitment.

### Already done

- **What is in S3 Ceph** is mapped: folders, 227 tables, sizes, freshness, and where malaria and RMNCAH-N data sits (`docs/exploration/`).
- **A repeatable explorer** exists for inventories, change tracking, profiling and ad-hoc queries (`explorer/`).
- **The name, source, storage and infrastructure** are decided (`planning/README.md`).

### Weeks 1 to 2: inventory and mapping

- Profile the patient and encounter tables in all three EMRs: row counts, empty rates, the values in use for sex and county, and which identifier types patients carry. The explorer's `profile` command does this.
- Write the mapping spec for **patient and encounter only**.
- Confirm, by reading data, which codes, test names and form fields identify malaria and the RMNCAH-N measures (the "still to confirm" lists in the exploration pages).
- Stand up the proof-of-concept environment: SeaweedFS, Lakekeeper, Trino, dbt, Dagster.
- Put the open questions to DHA (the list in `docs/exploration/README.md`).

Done when: the mapping spec for patient and encounter is agreed, and every proof-of-concept indicator has a named source or a named gap.

### Weeks 3 to 5: bronze

- Build the pick-up from S3 Ceph for the tables the first slice needs.
- Prove replay: rebuild a bronze table from scratch and get the same result.
- Write the shared macros for soft-deleted rows and time zones.
- Build the first interim source bridges: KHIS and population projections.
- Run the five SeaweedFS tests in the components paper.

Done when: bronze is loading on a schedule, a replay matches, and SeaweedFS has passed its tests.

### Weeks 6 to 9: silver for patient and encounter

- Staging models for patient, facility and encounter from each EMR.
- Hubs, links and satellites for those three; point-in-time tables.
- Master Patient Index: exact matching on UPI and secondary identifiers for all sources; scored matching for Tiberbu; the same-as link and steward queue.
- `silver_patient`, `silver_facility`, `silver_encounter`, de-identified, with quality rules.
- dbt docs published; OpenMetadata reading from dbt and the catalog.
- Then the event tables the twelve indicators need: diagnosis, lab test, prescription, maternal contact, delivery, immunisation, death.

Done when: an analyst can query one person's encounters across all three systems by `person_key`, and the quality checks pass after each load.

### Weeks 10 to 12: gold for the proof of concept

- Dimensions and the facts for the twelve proof-of-concept indicators.
- The indicator tables, loaded to ClickHouse; the twelve indicators defined in the Indicator Registry.
- A first programme dashboard for malaria and for RMNCAH-N, and a first Intelligence Centre view.
- **Reconcile against KHIS for one month.** Where NHAI and KHIS differ, explain why. The commonest cause is whether an indicator counts patient records or persons.

Done when: the twelve indicators show on a dashboard, each traceable to its source rows, with a written reconciliation against KHIS.

### Week 13 onwards: repeat and widen

- Complete each programme's indicator set, then its Programme Intelligence Hub (self-service, maps, governed extracts).
- Add programmes one at a time: HIV, TB, supply chain. Each adds its own facts and reuses the shared dimensions.
- Extend the vault to provider, diagnosis, order and claim only if it proved its worth on patient and encounter.
- Retire each interim source bridge when DHA stages that source in S3 Ceph.

## Things that will take longer than expected

From the technology discussion:

- AMRS address columns not matching KenyaEMR's.
- Tiberbu links that point at nothing, because it does not enforce them.
- Vitals stored as text.
- Tiberbu record numbers restarting each year, so they cannot be used for ordering.

From the exploration of S3 Ceph:

- KenyaEMR's `orders` table was restarted on 7 November 2026 and holds two days of loads, so prescriptions cannot be tied to patients from it.
- Tiberbu's forms table may be incomplete after its restart on 30 July 2026.
- Names and addresses are not staged for KenyaEMR or AMRS, which limits patient matching to identifiers.
- KHIS in S3 Ceph stops at June 2026 and has no malaria indicators.
- No population denominators are staged.
- The link from a KenyaEMR facility database to a Master Facility List code has not been found.
